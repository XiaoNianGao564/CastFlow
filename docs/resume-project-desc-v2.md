## 推荐简历正文（约520字）

**CastFlow —— 自迭代多智能体电力负荷预测平台**

**项目角色**：独立设计开发（全栈） | **时间**：2025.10 - 至今 | **GitHub**：github.com/XiaoNianGao564/CastFlow

**技术栈**：TypeScript · Bun · Hono · SolidJS · Python · pandas · statsmodels · scikit-learn · Prophet · XGBoost · MySQL · Qwen · SSE

**项目简介**：针对传统机器学习预测 pipeline 人工调参效率低、模型选择依赖经验、调优过程不可复用的问题，独立设计并落地一套基于多智能体协作的自迭代时序预测系统。采用自研编排器（非 LangChain/LangGraph 框架），调度 12 个专用 Agent 协同工作，支持 4 种编排模式，覆盖数据诊断 → 代码生成 → 沙箱执行 → 误差评估 → LLM 补丁 → 迭代收敛的完整闭环，应用于铜川市五区县电量负荷预测场景，实现端到端自动化运行零人工干预。

**核心贡献**：

- **自研多 Agent 编排架构**：独立设计 Coordinator 调度 12 个专用 Agent（数据诊断、代码生成、沙箱执行、误差评估、根因分析、补丁生成、模型选择等），实现 Full Loop 经典闭环、ReAct 动态规划（内置 11 个工具）、3-Agent 温度分层流水线（Planner 0.3 / Forecaster 0.6 / Critic 0.2）、多模型并行迭代四种编排策略，通过温度分层控制各环节创造性与精确性平衡，避免单一温度导致的过保守或过激进问题；

- **代码级自迭代优化机制**：不同于传统超参数搜索，系统由 LLM 生成最小化代码补丁（仅修改模型参数、数据预处理逻辑、特征工程与模型结构，绝不重写全文），结合确定性正则修复引擎（<1ms 覆盖常见语法错误与参数越界，减少 90%+ 的 LLM 调用开销）与空补丁检测机制（连续 3 次空补丁强制触发兜底策略并切换模型），配合最优版本回滚（非提升迭代自动回滚至历史最优），确保预测准确率从初始基线持续收敛至 90%+，同时单轮迭代 LLM 调用成本降低 90%；

- **智能模型选择与并行评估**：基于数据 6 维特征画像（季节强度、趋势方向、趋势强度、波动性、区县数、历史年份）为 31 个预测模型池（SARIMA、Prophet、XGBoost、LightGBM、ETS、Holt-Winters、MLP、集成模型等）动态打分排序，自动选择 Top-K 候选模型，支持 Top-3 模型并行预测与并行迭代，取全局最优结果进入下一轮优化，避免从单一模型顺序试错造成的迭代浪费；

- **三层记忆与知识沉淀系统**：构建 ExperienceStore（记录有效/无效策略及副作用标签）、SkillStore（固化数据特征-策略指纹，支持 6 维特征加权匹配检索，跨项目经验复用）、RAGStore（TF-IDF 字符 n-gram 向量化 + cosine similarity 检索历史分析文档）三层互补记忆体系，实现跨会话经验沉淀与复用，新任务启动时自动注入历史有效策略与踩坑记录，避免重复踩坑；

- **安全沙箱与数据完整性保障**：Python 预测代码在独立子进程中沙箱执行，输入数据经过完整性校验（5 区县齐全、无零值、至少 12 个月历史），输出结果经过格式校验与异常值检测，确保系统稳定运行不崩溃；执行超时自动终止并回退到安全版本；

- **实时监控 Dashboard 与工程落地**：基于 SolidJS + Tailwind CSS + Vite 构建前端监控面板，通过 SSE 流式推送实时迭代日志、准确率趋势折线图与区县级预测对比视图，后端 Hono API 提供 REST + SSE 双通道通信，MySQL 存储源数据，JSON 文件存储迭代记录，实现一键启动端到端闭环运行，系统可独立部署运行。

## 面试话术（基于上述简历展开）

**面试官可能问**："你说自研编排器，和 LangGraph 有什么区别？"
**回答**："LangGraph 是通用框架，节点和边都是固定的。我的编排器是针对预测场景专门设计的——比如温度分层，Planner 用 0.3 做数据诊断和模型选择（要精确），Forecaster 用 0.6 做代码生成（要创造性尝试新思路），Critic 用 0.2 做最终审查（要严格）。三种温度在同一个闭环里协作，这是 LangGraph 没有的原生支持。另外我的 ReAct 模式内置了 11 个工具，包括 load_data、web_search、switch_model 这些预测专用工具，不是通用的。"

**面试官可能问**："你说减少 90% LLM 调用，具体怎么做的？"
**回答**："大部分生成的代码错误其实是那几种：括号不匹配、字符串没闭合、maxiter 设置太小。我用正则规则在 <1ms 内修复这些，只有遇到全新错误模式才调 LLM。另外如果 LLM 连续 3 次生成的补丁和原代码一样（空补丁），系统会强制触发兜底策略——直接换模型，不浪费 Token 在同一个死胡同里。"

**面试官可能问**："这个项目的实际应用场景是什么？"
**回答**："铜川市电力公司的五区县电量负荷预测。传统做法是人选一个模型、调参、跑预测、人工对比误差、再调参，一轮可能要几小时。我的系统把整个过程自动化了——从数据读取到生成报告全部自动，一个按键启动后可以去干别的，准确率自己越迭代越高。"
